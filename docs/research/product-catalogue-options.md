# Product catalog options for the Indian packaged-food demo

> Status: historical notes. Banner added 2026-09-26; the catalog acquisition plan is retained for context and current behaviour lives in `backend/README.md`.

**Decision for the 24-hour prototype:** use Open Food Facts (OFF) as a best-effort, read-only discovery source; cache exact barcode responses in PostgreSQL with raw payload and provenance; and use a small set of operator-reviewed Indian package observations for deterministic demo coverage. Keep manual label capture/correction as the miss path. Do not use IFCT, recipes, barcode-name websites, or an LLM to invent packaged-label facts. Do not tell a user that an unobserved value is safe.

This is a catalog acquisition plan, not evidence that any public source covers every Indian SKU. We checked the current repository adapters and the bounded source verification in [adapter-validation-2026-09-26.md](../source-verification/adapter-validation-2026-09-26.md). The older [project notes](hidden-ingredient-risk-app-notes.md) contain useful history, but several source/coverage claims in them should not be treated as current validation.

## What counts as a usable catalog record?

A barcode-to-name hit is an identity hint. A product suitable for personalized assessment needs more: a matching barcode and exact variant, ingredient and precautionary statements, nutrient values with unit and serving basis, source/retrieval and modification time, and a record of what was actually reviewed. Missing panel fields stay **unknown**. A catalogue label such as “sugar-free,” a brand match, a product image, a nutrition score, or an LLM guess does not establish ingredient or nutrient evidence.

For swaps, candidate completeness is stricter still: same known product category; enough comparable nutrients on the same basis; complete ingredient and precautionary checks for the user's active restrictions; no unresolved relevant allergen; and an explicit reason it improves on the scanned product. If there are no eligible records, return “no verified match yet.” Never compare an unknown sodium or carbohydrate value as though it were zero.

## Exact integration paths and checks

OFF's current documentation recommends v3 for new integrations. The supported barcode operation is `GET https://world.openfoodfacts.org/api/v3/product/{code}` with a `fields` list and an identifying `User-Agent`; `cc=IN` can request country-localized fields but does not prove Indian market coverage. v2 structured search is supported but deprecated; v2 does **not** provide full-text search. The current OFF documentation still identifies `/cgi/search.pl` as the legacy full-text search route. The existing adapter uses v3 barcode lookup and that legacy route for name search; keep name search debounced/on-submit and use PostgreSQL search first.

OFF documents limits of 15 product-read requests/minute/IP and 10 search requests/minute/IP, says not to use search for type-ahead, and may deny requests when limits are exceeded. If fetching more than a few hundred products, it asks clients to use CSV/JSONL; apps with higher traffic are encouraged to host a local instance/custom backend and refresh from daily exports. The API has no read key, but use the custom `User-Agent`, review reuse terms, attribute OFF, and review ODbL/database-contents licensing before redistributing a derived catalogue. Product images have separate CC BY-SA and possible third-party rights. See [OFF API usage and limits](https://openfoodfacts.github.io/openfoodfacts-server/api/) and [OFF license guidance](https://openfoodfacts.github.io/openfoodfacts-server/api/tutorials/license-be-on-the-legal-side/).

The exact routes currently exercised in our repo are:

```text
GET https://world.openfoodfacts.org/api/v3/product/{barcode}.json?fields=...
GET https://world.openfoodfacts.org/cgi/search.pl?search_terms=...&search_simple=1&action=process&json=1&page_size=...
GET https://api.apify.com/v2/actor-runs/{run_id}
GET https://api.apify.com/v2/datasets/{dataset_id}/items?format=json&limit=...&offset=...
```

The Apify GET endpoints are documented and the supplied completed run was read successfully; these are **read existing data** calls. Starting an actor is a separate POST that creates a run and can incur platform/actor usage. Apify pricing docs confirm runs, dataset reads, storage, and compute may contribute to usage; we should not start one without an explicit budget. See [Apify Get run](https://docs.apify.com/api/v2/actors-run-get), [dataset items](https://docs.apify.com/api/v2/dataset-items-get), and [Apify pricing](https://apify.com/pricing).

### What we actually verified

- OFF v3 returned one live record for `3017620422003`; sodium source `0.0428 g` was normalized by the adapter to `42.8 mg` at an explicit 100 g basis. That verifies the integration path, not broad Indian coverage.
- Barcode `8909081007163` was absent from our local product table, and direct OFF v3 and v2 requests returned 404 in the source audit. The observed client text “Bingo Tedhe Medhe Masala Tadka” / `salt: 732.6` has no matching saved record or source trace yet. Do not state that the value is verified, nor assume it is from OFF. See [barcode verification](../source-verification/barcode-8909081007163.md).
- The existing Apify run `svCjf5DtStMudLn88` succeeded and exposed one OFF-scraped Bhujia item (`8904004400052`). Its flattened `sodium_100g: 788` lacked unit and nutrition-basis metadata. We preserve the raw item, but normalized nutrients remain unknown.
- The Food.com Apify actor listing was reachable; its checked input-schema route returned 404 and no completed recipe dataset was validated. Even a working recipe corpus would support recipe/dish work, not barcode-based packaged-product lookup.
- IFCT's selected source files were downloaded and imported twice with 542 reference-food rows each time. Official NIN publishes the [IFCT 2017 source PDF](https://www.nin.res.in/ebooks/IFCT2017.pdf); the importer uses the [nodef transcription](https://github.com/nodef/ifct2017), not package labels.

## 24-hour ingestion and coverage plan

1. **Seed the demo with a deliberately small, useful catalogue.** Pick roughly 20–40 real packaged products the team can inspect physically (prioritize categories with plausible swaps such as biscuits/crackers, breakfast cereal, spreads). Record exact variant, GTIN/barcode, front and full ingredient/advisory/nutrition panels, basis, package/source evidence, reviewer, review timestamp, and source/license. Keep each file entry operator-reviewed; the existing `reviewed-products` importer requires a category, complete ingredient and advisory review, and manual source provenance. Do not seed fake labels just to make recommendations appear plentiful.
2. **At scan time, validate barcode, check PostgreSQL, then make one bounded OFF v3 lookup on a cache miss.** Set an identifiable `User-Agent`, request only needed fields, and save the raw JSON, OFF reference, retrieved time, source modified time when present, and normalized observation together. Cache misses, 404s, timeouts, and invalid fields remain distinct states; a miss is not “safe.” Do not put credentials in mobile requests.
3. **When neither source has a suitable record, show an explicit incomplete result.** Let the user capture front, ingredients, allergen/advisory, and nutrition panels or type them in. OCR/LLM may propose a structured draft and highlight ambiguous aliases, but raw OCR/model output is unverified until the user confirms/corrects it. Preserve original text, corrected fields, extraction/model metadata, image ownership/retention consent, and review state. Do not upload user package photos to OFF automatically.
4. **Only compare reviewed/imported records as replacements.** Start with curated same-category sets. Apply all restrictions and explicit clinician limits deterministically before ranking; relevant unknowns disqualify a candidate. Display why it was selected and which values/bases support the comparison. If coverage is insufficient, return no candidate and say which evidence is missing.
5. **Track scope and freshness.** Show source and last-refresh/review date in product detail. If the package or source record has changed, mark stale and request re-check. Maintain a small coverage table for demo set: products per category, complete label count, required nutrient coverage, allergen coverage, and eligible-swap pairs. Avoid a headline “all products” claim.

The existing integrations already preserve raw OFF/Apify records, keep the Apify flattened nutrients unknown, import IFCT to `ReferenceFood` only, and expose a reviewed-product import path. The recommendation service uses explicit categories and candidate eligibility; the allow-listed OFF category map is small and unknown categories correctly yield no category match. For extensibility, keep source adapters separate and normalize into a common observation plus an immutable provenance snapshot; do not let upstream source quality become a clinical certainty score.

## Later acquisition work

For a post-demo catalogue, first measure real Indian coverage with a stratified sample of GTINs from store shelves (major national and regional brands, multiple product groups), then compare exact-variant hit rate and completeness rather than raw API response counts. Ask GS1 India/DataKart and selected manufacturers for an authorized read-only feed/pilot with field schema, version/effective dates, product/country-market matching, update cadence, attribution, redistribution/caching terms, deletion policy, and contact for corrections. GS1 describes DataKart sharing brand-owner records with connected platforms and Smart Consumer, while its premium product-data exchange is subscription-based; public pages reviewed do not establish a general public developer query API. GDSN material describes participant synchronization, not anonymous catalogue search. See [GS1 DataKart](https://www.gs1india.org/services/datakart), [DataKart Premium](https://admin.gs1india.org/uploads/Data_Kart_Premium_Service_new_90dd979378.pdf), and [GS1 GDSN](https://support.gs1.org/support/solutions/articles/43000734253-what-is-the-global-data-synchronisation-network-gdsn-).

Before adopting a commercial provider, run the same small India GTIN sample through it, inspect every claimed allergen/nutrition field against photographed current packaging, establish redisplay and storage rights, and compute the cost per **complete usable record**, not per barcode hit. Do not assume Barcode Lookup's worldwide barcode catalog guarantees Indian ingredient panels; its API requires a key and its listed monthly tiers start at $99 for 5,000 calls ([API product fields and pricing](https://www.barcodelookup.com/api), [API syntax](https://www.barcodelookup.com/api-documentation)).
